# Solution Strategy: СтройУправ

Стратегический анализ ключевых решений проекта: SCQA, first principles, технические trade-offs, TRIZ-противоречия.

---

## 1. SCQA Framework

### Situation (Ситуация)

Строительная отрасль РФ -- 16.8 трлн рублей (2024). Рынок ПО для управления строительством -- 6.4 млрд рублей с прогнозом x4 к 2028 году. BIM/ТИМ обязателен с 2024 года, что запустило принудительную цифровизацию. 37% строительных компаний уже используют элементы ИИ. При этом 70% рынка ПО занимают российские решения (импортозамещение после ухода западных вендоров).

Odoo -- ведущая open-source ERP (13M+ пользователей, $650M ARR), но не имеет строительных модулей из коробки и фактически ушла с российского рынка.

### Complication (Осложнение)

Ремонтные и строительные компании РФ (5-500 чел.) управляют проектами через набор из 5-7 разрозненных инструментов: Excel для смет, WhatsApp для координации бригад, 1С:Бухгалтерия для учёта, бумажные журналы для фотофиксации, телефонные звонки для отчётности. Это приводит к:

- **40% заказчиков** жалуются на срывы сроков и скрытые доплаты
- **Потеря данных** при уходе прораба (информация в голове / в личном телефоне)
- **Ночные Excel-сводки** -- руководители тратят 2-3 часа ежедневно на ручной свод
- **Сметы за 2-5 дней** -- ручной расчёт по ГЭСН/ФЕР с бумажными справочниками
- **Убыточные объекты** из-за непрозрачного бюджетного учёта (отклонения видны постфактум)

Существующие решения (1С:УСО, АЛТИУС, Аспро.Cloud, LegkoRem) либо desktop-only и монолитные, либо не имеют AI-сметчика по российским нормативам, либо не mobile-first.

### Question (Вопрос)

Как создать mobile-first ERP для строительства и ремонта, которая: (1) генерирует AI-сметы по ГЭСН/ФЕР за минуты вместо дней, (2) даёт прозрачность бюджета в реальном времени, (3) работает с телефона на стройплощадке, (4) соответствует 152-ФЗ и российским сметным нормативам -- и при этом может быть построена за 90 дней командой из 8 человек?

### Answer (Ответ)

**СтройУправ** -- форк Odoo Community (LGPL-v3) с российскими строительными модулями поверх проверенного ERP-ядра:

1. **AI-сметчик** на Cloud.ru Foundation Models (Qwen3-Coder + RAG по ГЭСН/ФЕР) -- смета за 5 минут вместо 5 дней
2. **Dashboard объектов** с real-time бюджетом факт/план и AI-алертами при отклонениях
3. **PWA-приложение** для прорабов: фотофиксация с геотегом, управление задачами, offline-режим
4. **Портал заказчика** (view-only) -- прозрачность как конкурентное преимущество и viral-механизм
5. **Данные в РФ** через Cloud.ru -- compliance с 152-ФЗ без компромиссов

Бизнес-модель: freemium (AI-смета = lead magnet с нулевым CAC) -> SaaS-подписки (2 990 -- 49 900 руб/мес). Unit economics: LTV:CAC 5.7:1, payback 3.2 месяца.

## 2. First Principles Analysis

### Почему Excel + WhatsApp + 1С не работает для строительства?

Разбираем проблему до базовых элементов:

**Принцип 1: Данные рождаются на стройплощадке, а обрабатываются в офисе.**

Строительство -- одна из немногих отраслей, где место создания данных (стройплощадка, пыль, грязь, телефон в руке) радикально отличается от места их обработки (офис, Excel, большой экран). Excel не работает с телефона. WhatsApp не имеет структуры. Данные теряются при передаче.

Следствие: система ОБЯЗАНА быть mobile-first с offline-поддержкой. Не "mobile-responsive", а "mobile-native".

**Принцип 2: Смета -- это перевод с языка строительства на язык денег.**

Сметный расчёт по ГЭСН/ФЕР -- это формализованное отображение: "работа X в объёме Y" -> "расценка Z * индекс I * коэффициенты K". Эта задача:
- Детерминированная (для одних входов -- одни выходы)
- Нормативно регулируемая (ГЭСН, ФЕР, ТЕР, индексы Минстроя)
- Рутинная (тысячи одинаковых расчётов)

Это идеальная задача для AI: NLP парсит описание -> RAG находит расценки -> формула считает итог. Человек-сметчик тратит 2-5 дней; AI -- 5 минут. Человек нужен для проверки, не для расчёта.

**Принцип 3: Прозрачность создаёт доверие, доверие создаёт retention.**

Заказчик ремонта боится двух вещей: обмана с деньгами и срыва сроков. Если дать ему портал с real-time прогрессом и фото -- страх уходит. Более того:
- Заказчик, привыкший к порталу, ТРЕБУЕТ его от следующего подрядчика
- Это создаёт supply-side viral: новый подрядчик регистрируется ради заказа
- Network effect: больше подрядчиков -> больше заказчиков -> больше подрядчиков

**Принцип 4: 1С -- это бухгалтерия, не операционное управление.**

1С:Бухгалтерия решает задачу финансового учёта (проводки, НДС, отчётность). 1С:УСО решает задачу управленческого учёта в строительстве, но это desktop-монолит. Строителям нужен ОПЕРАЦИОННЫЙ слой: задачи бригадам, фото с объекта, бюджет в реальном времени. Этот слой НЕ заменяет 1С -- он дополняет.

Следствие: не пытаться заменить 1С:Бухгалтерию, а интегрироваться (экспорт/импорт). Конкурировать с 1С:УСО на уровне UX и mobile.

**Принцип 5: Time-to-market важнее идеальной архитектуры.**

Окно возможностей: рынок x4 к 2028, импортозамещение, обязательный BIM. Каждый месяц задержки -- это потенциальный конкурент, занявший нишу. Odoo Community дает 80% ERP-функционала "из коробки" (CRM, проекты, задачи, бухгалтерия, склад). Строить с нуля -- 12+ месяцев. Форкнуть Odoo -- 3 месяца до MVP.

Следствие: fork Odoo для MVP, постепенная замена frontend на React для масштабирования.

## 3. Key Technical Decisions

### Decision 1: Fork Odoo Community vs Custom Build

| Критерий | Fork Odoo | Custom (Python/FastAPI) | Выбор |
|----------|:---------:|:----------------------:|:-----:|
| Time-to-market | 3 мес | 9-12 мес | Odoo |
| ERP из коробки (CRM, HR, склад, бух.) | Да | Строить с нуля | Odoo |
| Модульная архитектура | Odoo modules (зрелая) | Строить с нуля | Odoo |
| PostgreSQL ORM | Odoo ORM (специфичный) | SQLAlchemy (стандартный) | Custom лучше |
| Frontend гибкость | OWL (ограниченный) | React/Vue (полная) | Custom лучше |
| AI-интеграция | Возможно, но Odoo ORM мешает | Нативно | Custom лучше |
| Сообщество / плагины | 40K+ модулей | Ноль | Odoo |
| Масштабируемость | Средняя (monolith) | Высокая (microservices) | Custom лучше |

**Решение:** Fork Odoo Community для MVP (Day 0-90). Odoo даёт 80% нужного функционала из коробки. На этапе Scale (M12+) -- постепенная миграция frontend на React, выделение AI-модуля в отдельный сервис.

**Риск:** Lock-in в Odoo ORM. Митигация: AI-сметчик с первого дня как отдельный FastAPI-сервис, не зависящий от Odoo ORM.

### Decision 2: Cloud.ru vs OpenAI/Anthropic для AI

| Критерий | Cloud.ru | OpenAI | Выбор |
|----------|:--------:|:------:|:-----:|
| Данные в РФ (152-ФЗ) | Да | Нет | Cloud.ru |
| Стоимость (за 1M tokens) | 35-70 руб | 250-1000 руб (через VPN) | Cloud.ru (x7-x14 дешевле) |
| Fine-tuning на ГЭСН/ФЕР | Да (без экспорта данных) | Да (данные уходят за рубеж) | Cloud.ru |
| Managed RAG | Да (готовый сервис) | Нет (строить самим) | Cloud.ru |
| Качество моделей | Qwen3-480B -- сопоставимо с GPT-4o | GPT-4o -- best-in-class | OpenAI для edge cases |
| Надёжность API | 15 RPS, молодой сервис | 60 RPS, зрелый | OpenAI надёжнее |
| Санкционные риски | Нет | Да (блокировка РФ IP) | Cloud.ru |

**Решение:** Dual-provider через OpenAI-compatible client (env-based switch). Cloud.ru primary (70-80% запросов), OpenAI fallback (для R&D и edge cases). Переключение -- одна строка конфига.

**Обоснование:** Суверенность данных -- не опция, а требование (строительная документация, персональные данные заказчиков). Cloud.ru в 7-14 раз дешевле. Fine-tuning на реальных сметах без экспорта данных за рубеж.

### Decision 3: PWA vs Native App

| Критерий | PWA | Native (React Native) | Выбор |
|----------|:---:|:---------------------:|:-----:|
| Time-to-market | 2 нед | 6-8 нед | PWA |
| Установка | Без App Store | Через App Store | PWA проще |
| Offline-режим | Service Workers | Full offline | Обе могут |
| Камера + GPS | Да (Web API) | Да (нативно) | Обе могут |
| Push-уведомления | Да (Web Push) | Да (FCM/APNs) | Обе могут |
| UX на стройке (грязные руки, яркое солнце) | Средне | Лучше | Native лучше |
| Обновления | Мгновенно | Через App Store (review) | PWA |
| Одна кодовая база | Да (+ web) | Отдельная | PWA |

**Решение:** PWA для MVP (Day 0-60). React Native для Scale (Day 60+). PWA покрывает 90% use cases прораба (фото, задачи, dashboard). Native нужен для push-уведомлений на iOS и лучшего UX.

### Decision 4: PostgreSQL (единственная СУБД)

Не обсуждается: Odoo поддерживает ТОЛЬКО PostgreSQL. Это совпадает с потребностями проекта:
- Проверено на 13M+ пользователей Odoo
- Поддержка JSONB для гибких схем (сметные данные, метаданные фото)
- Full-text search для поиска по ГЭСН/ФЕР (+ pgvector для embedding)
- PostGIS для геоданных (валидация координат фото)

### Decision 5: Monorepo vs Polyrepo

**Решение:** Monorepo (distributed monolith).

Обоснование: команда 8 человек, один продукт, общая база данных. Polyrepo создаёт overhead на CI/CD, версионирование, inter-service contracts. Monorepo с Docker Compose -- простейший путь к production для малой команды. При росте до 20+ разработчиков -- выделение AI-сервиса в отдельный repo.

## 4. TRIZ-противоречия

### Противоречие 1: Точность AI-смет vs Скорость генерации

**Параметр, который хотим улучшить:** Точность сметы (target: >= 85% совпадение с ручным расчётом).

**Параметр, который ухудшается:** Время генерации (target: < 60 сек).

**Текущее состояние:** Чем больше проверок, перекрёстных валидаций и RAG-запросов -- тем точнее смета, но тем дольше генерация.

**TRIZ-решение (Принцип 1: Сегментация):**
- Разбить генерацию на 2 этапа: быстрый черновик (< 10 сек, точность 70%) + уточнённая смета (< 60 сек, точность 85%)
- Пользователь видит черновик мгновенно, уточнённая версия подгружается в фоне
- Для "быстрого взгляда" хватает черновика; для отправки заказчику -- уточнённая

**TRIZ-решение (Принцип 35: Изменение параметров):**
- Fine-tuning модели на реальных сметах (data flywheel) -- со временем модель становится точнее БЕЗ увеличения времени
- Чем больше пользователей -> больше реальных смет -> точнее модель -> быстрее inference (меньше retry)

### Противоречие 2: Простота интерфейса vs Глубина функционала

**Параметр, который хотим улучшить:** Простота UX (прораб с грязными руками, 3 минуты на объекте).

**Параметр, который ухудшается:** Полнота функций (руководителю нужны 50+ отчётов, бюджеты, Gantt).

**Текущее состояние:** Если показать все функции -- интерфейс перегружен и пугает. Если спрятать -- руководитель не найдёт нужное.

**TRIZ-решение (Принцип 3: Локальное качество):**
- Onboarding quiz (4 вопроса) определяет роль: прораб видит 5 экранов, руководитель -- 15
- Интерфейс адаптируется под роль, но все функции доступны через поиск
- Progressive disclosure: начинаем с задач и фото (прораб), открываем аналитику по мере вовлечения

**TRIZ-решение (Принцип 17: Переход в другое измерение):**
- Desktop = аналитика, отчёты, сметы (руководитель в офисе)
- Mobile = задачи, фото, чат (прораб на объекте)
- Один продукт -- два совершенно разных UX для двух контекстов

### Противоречие 3: Бесплатный доступ vs Монетизация

**Параметр, который хотим улучшить:** Охват (максимум пользователей для network effect).

**Параметр, который ухудшается:** Выручка (бесплатные пользователи не платят).

**Текущее состояние:** Freemium (1 объект + 3 AI-сметы бесплатно). Если лимиты слишком щедрые -- никто не платит. Если слишком жёсткие -- не приходят.

**TRIZ-решение (Принцип 22: Обратить вред в пользу):**
- Бесплатная AI-смета = lead magnet с нулевым CAC. Каждая смета -- это контакт потенциального клиента
- Branded PDF "Создано в СтройУправ" = бесплатная реклама при отправке заказчику
- Бесплатные пользователи создают данные (сметы), которые улучшают AI-модель для платных

**TRIZ-решение (Принцип 10: Предварительное действие):**
- Trial 14 дней с ПОЛНЫМ доступом -> привыкание -> switching cost -> конверсия
- "Привыкание" = данные (объекты, сметы, фото) уже в системе -> сложно уйти
- AI-алерт на 12-й день: "У вас 3 объекта и 47 фото -- при переходе на Free вы потеряете доступ к 2 объектам"

### Противоречие 4: Суверенность данных vs Качество AI

**Параметр, который хотим улучшить:** Compliance (данные в РФ, 152-ФЗ).

**Параметр, который ухудшается:** Качество AI (лучшие модели у OpenAI/Anthropic, серверы за рубежом).

**TRIZ-решение (Принцип 5: Объединение):**
- Dual-provider через OpenAI-compatible client: Cloud.ru для production данных, OpenAI для R&D/бенчмарков
- Fine-tuning на Cloud.ru: модель обучается на российских данных БЕЗ экспорта -> со временем quality gap сокращается
- RAG по ГЭСН/ФЕР на Cloud.ru Managed RAG: domain-specific knowledge компенсирует разницу в "общем интеллекте" модели

### Противоречие 5: Speed-to-market vs Архитектурная чистота

**Параметр, который хотим улучшить:** Скорость выхода на рынок (MVP за 90 дней).

**Параметр, который ухудшается:** Архитектурная гибкость (Odoo ORM = legacy, OWL = ограничения).

**TRIZ-решение (Принцип 15: Динамичность):**
- Fork Odoo для MVP (80% из коробки)
- AI-сметчик с Day 1 как отдельный FastAPI-сервис (не зависит от Odoo ORM)
- Постепенная замена OWL -> React для customer-facing экранов
- Архитектура "strangler fig": новые модули на FastAPI/React, старые на Odoo, coexist

## 5. Trade-offs and Rationale

### Trade-off 1: Odoo Fork

| За (Pros) | Против (Cons) |
|-----------|---------------|
| ERP-ядро из коробки: CRM, проекты, бухгалтерия, склад | Lock-in в Odoo ORM (не стандартный SQLAlchemy) |
| 40K+ модулей в экосистеме | OWL framework ограничивает frontend |
| Проверено на 13M+ пользователей | Odoo Community обновляется ежегодно -- нужно мержить |
| LGPL-v3 -- можно форкнуть коммерчески | Специфичный стек: Python + OWL + QWeb |
| PostgreSQL = наш выбор в любом случае | Odoo ORM тяжёлый для AI-нагрузок |

**Решение:** Форк для MVP. Главный риск (lock-in) митигируется тем, что AI-модуль -- отдельный сервис с первого дня.

### Trade-off 2: Cloud.ru как Primary AI Provider

| За (Pros) | Против (Cons) |
|-----------|---------------|
| Данные в РФ (compliance 152-ФЗ) | Молодой сервис, менее надёжный чем OpenAI |
| x7-x14 дешевле OpenAI | Rate limit 15 RPS (vs 60 RPS у OpenAI) |
| Fine-tuning без экспорта данных | Меньше выбор моделей |
| Managed RAG готовый сервис | Документация беднее |
| Нет санкционных рисков | Vendor lock-in в российского провайдера |

**Решение:** Cloud.ru primary + OpenAI fallback. OpenAI-compatible client (env-based switch) делает переключение тривиальным. Если Cloud.ru упадёт или не справится -- переключение за секунды.

### Trade-off 3: PWA first, Native later

| За (Pros) | Против (Cons) |
|-----------|---------------|
| Одна кодовая база (web + mobile) | Нет доступа к некоторым native API |
| Мгновенные обновления (без App Store) | Push-уведомления на iOS ограничены |
| Установка без скачивания | UX хуже чем native на стройке |
| Быстрый time-to-market (2 недели) | Offline-режим сложнее чем в native |
| Работает на любом устройстве | Не видна в App Store / Google Play (discovery) |

**Решение:** PWA для MVP. 90% задач прораба (фото, задачи, dashboard) работают через PWA. React Native добавляется на Day 60+ для push-уведомлений и присутствия в сторах.

### Trade-off 4: Freemium vs Paid-only

| За (Pros) | Против (Cons) |
|-----------|---------------|
| AI-смета = lead magnet с нулевым CAC | Бесплатные пользователи нагружают GPU |
| Viral через branded PDF | Конверсия free->paid ~8% (92% не платят) |
| Data flywheel: бесплатные сметы улучшают модель | Поддержка бесплатных пользователей |
| Network effect через маркетплейс | Каннибализация: "зачем платить, free хватает" |

**Решение:** Freemium с жёсткими лимитами (1 объект, 3 сметы/мес). Достаточно для "Aha moment", недостаточно для реальной работы. Trial 14 дней с полным доступом создаёт привыкание.

### Trade-off 5: Monorepo Distributed Monolith vs Microservices

| За (Pros) | Против (Cons) |
|-----------|---------------|
| Простота для команды из 8 человек | Масштабирование ограничено |
| Один деплой (Docker Compose) | AI-нагрузка конкурирует с ERP за ресурсы |
| Общая БД -- нет inter-service contracts | Единая точка отказа |
| Проще дебажить и тестировать | Сложнее выделить модуль позже |

**Решение:** Distributed monolith для MVP. AI-сметчик как отдельный Docker container (FastAPI), но в одном docker-compose.yml. При росте до 10K пользователей -- выделение в отдельный сервис.

### Trade-off 6: Ежеквартальное обновление индексов vs Real-time

| За real-time (Pros) | За ежеквартального (Pros) |
|---------------------|--------------------------|
| Сметы всегда актуальны | Индексы Минстроя публикуются квартально |
| Конкурентное преимущество | Простота реализации |
| Автоматический пересчёт | Предсказуемость для пользователей |

**Решение:** Ежеквартальное обновление (в соответствии с графиком Минстроя) + push-уведомление пользователям: "Новые индексы -- пересчитайте сметы". Real-time невозможен, потому что источник данных (Минстрой) публикует квартально.
